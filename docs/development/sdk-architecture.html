The Short Version

The SDK keeps standards logic in spec namespaces and exposes common workflows through cross-spec facades. Python imports, CLI commands, and MCP tools all reuse those facades, which keeps behavior consistent for people, scripts, and agents.

Cross-Spec Layer

This layer sits between consumer surfaces and the ODPS, ODPC, ODPG, ODPV, and ODPR namespaces. It lets Python users, CLI commands, MCP tools, and tests ask common questions without reimplementing document detection or response formatting.

agent.py

Detects the document type, loads the matching spec object, delegates validation and explanation, and resolves cross-spec references.

summary.py

Returns body-free artifact metadata: path, size, lines, hash, detected spec, kind, id, and compact-context sidecar references.

resources.py

Registers packaged schemas, prompts, examples, vocabulary records, catalog object guidance, and graph guidance under stable IDs.

results.py

Defines serializable output shapes such as ValidationResult, Reference, and Resource so every surface speaks the same language.

Namespaces

Namespaces are the ownership map inside `open_data_products`. Read them as a signal for where behavior belongs, not only as import paths.

open_data_products Public package root. Use this for supported imports and stable SDK API access.
odps ODPS product models, codecs, enums, normalization, and validation.
odpc Catalog loading, fragment collection, catalog building, rendered artifacts, and object guidance.
odpg Graph loading, building, conversion, validation, traversal, analysis, context, and explorer output.
odpv Vocabulary loading, term search, alias resolution, relationship checks, and context packets.
odpr Recipe, Provider, and RecipeCatalog validation, starter discovery, workspace init, explanation, dry-run planning, and guarded execution.
generation Prompts, source documents, provider config, LLM calls, artifact normalization, validation, and repair.
contracts Data Contract references, optional validation adapter, schema summaries, alignment, exports, and reports.
mcp Tool registry, stdio JSON-RPC server, ARWS manifest integration, and explicit safe or state-changing tool classes.
_activity.py Internal CLI evidence logging: workspace resolution, fixed activity lines, redaction, and rotating file writes.

Root modules such as `agent.py`, `summary.py`, `resources.py`, `pricing.py`, and `portfolio.py` handle cross-spec facades or product-level workflows. Underscored modules such as `_toon.py`, `_gcf.py`, `_activity.py`, `_io.py`, and `_search.py` are internal implementation helpers.

Core Layers

Public exports

`open_data_products/__init__.py` is the supported import surface. New public APIs are added explicitly.

Spec namespaces

ODPS models and validation, ODPC catalogs, ODPG graphs, ODPV vocabulary logic, and ODPR recipes live in their own folders.

Workflow modules

Generation, Data Contracts, portfolio workspaces, ODPR recipes, TOON, and GCF compose the spec modules into larger workflows.

Agent surfaces

CLI, MCP tools, and the ARWS manifest reuse the same SDK functions that Python users call directly. File-creating MCP tools are classified as state-changing.

Activity evidence

CLI command outcomes and LLM provider invocations are written as fixed lines in the resolved workspace activity log.

Shared result types

`ValidationResult`, `Reference`, and `Resource` give all surfaces predictable, serializable outputs.

Bundled resources

Schemas, prompts, examples, vocabulary records, object guidance, and graph records are registered in `resources.py`.

CLI Activity Evidence

The CLI writes workspace-local activity evidence through internal `_activity.py` helpers. By default, command outcomes append to `.open-data-products/activity.log` under the resolved workspace root. Each CLI invocation writes a terminal outcome line with classification, command id, exit code, duration, and redacted details. LLM-backed workflows also write an `[INFO]` `llm.invoke` line with the parent command, provider, provider type, model, and phase before the provider is called. This log is separate from MCP safe-tool behavior and uses Python standard-library rotating file handling.

ODPR Recipe Workflows

ODPR adds the workflow layer. `RecipeCatalog` documents are metadata-only discovery records, while full `Recipe` files remain the executable workflow contracts. Packaged starter recipes live under `open_data_products/odpr/data/starters/` and are discovered from the bundled `catalog.yaml`. Bare `recipe list` shows packaged starters when no local `recipes.config.yaml` is present, while `recipe list --config` keeps project catalog discovery. `recipe init` copies a starter into `./recipes/<starter-folder>/` by default, creating a user-owned workspace outside SDK internals. `recipe explain` inspects starter or local recipe metadata, steps, gates, safety notes, and next commands without executing steps or calling providers. Dry-runs expose explicit no-write and no-provider-call guarantees, planned reads and writes, gate and review summaries, execution/context policy, and required environment variables when provider configuration makes them knowable. `recipe plan` and `recipe dry-run` are CLI compatibility aliases for `recipe run --dry-run` and preserve the same JSON shape. When `recipe.yaml` exists in the current directory, `recipe plan`, `recipe dry-run`, `recipe validate`, and `recipe run` can use it without repeating the path. Guarded execution stays explicit: LLM-backed steps require `--allow-llm`, review-needed steps require `--approve-review`, and review approval never implicitly permits provider calls. `recipe run --approve-review` or `recipe run --allow-llm --approve-review` executes the selected recipe, while `--dry-run` keeps planning mode. Complete example workspaces live under `examples/recipes/workspaces/`; they are separate from packaged starters and each carries README, AGENTS, recipe, inputs, and outputs-example content. Parameterized starter initialization is advanced and opt-in: `recipe init --parameterized` adds recipe.values.yaml and values.schema.yaml while the default workspace stays self-contained around recipe.yaml.

1

Discover

List starter entries with `recipe list` or the safe MCP discovery tool.

2

Resolve

Match by catalog id, English name, or starter folder name.

3

Initialize

Copy README, AGENTS, and recipe.yaml into ./recipes/<starter-folder>/.

4

Explain

Use `recipe explain` to inspect metadata, steps, gates, and safety notes.

5

Plan

Use `recipe plan` to inspect reads, writes, env, gates, and providers before approval.

MCP `list_starter_recipes`, `check_starter_catalog`, and `explain_recipe` are safe. MCP `init_starter_recipe` is state-changing because it creates a local workspace and refuses existing output unless force is explicit.

Contributor Checklist

Behavior changes often touch more than one public surface. Update the owning module first, then add public exports, CLI wiring, MCP tools, ARWS classification, docs, and tests only when the behavior is part of those contracts.
